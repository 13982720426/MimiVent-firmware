# MimiVent 统计存储与 BLE 数据协议 V2 设计方案

**状态：** 设计稿，尚未实施。本文不代表现有固件和 App 已支持所述能力。

**目标：** 统一感应、操作、实际风机运行与统计的数据规则，减少 Flash 写入及 BLE 传输量，扩大可查询历史，并正确处理断电、重启、烧录、分页和校时。

**架构：** 固件保存有版本、序号和校验的分段二进制日志，通过小型恢复检查点恢复进行中的操作；独立维护小时和日汇总。App 通过版本化接口、稳定游标和增量同步读取数据，在本地完成展示分组。BLE 先采用数字枚举和紧凑 JSON 数组，按实际 MTU 分包。

**技术范围：** ESP32-C3、现有 Arduino/NimBLE/SPIFFS、Flutter App。保留 BLE、现有控制能力及双 OTA 应用槽。后续 STA、联网、其他客户端通过同一业务模型接入。

**默认保留：** 原始事件及操作明细 10 个本地自然日；小时、每日汇总 30 个本地自然日。允许配置为 15 天明细，但必须通过对应容量验收。

**数据升级：** 用户已允许清除旧统计，不要求迁移旧数据或兼容旧统计协议。格式切换需显式初始化统计区，并使 App 旧缓存失效；不以统计升级为由清除无关设备配置。

## 1. 范围与设计边界

本方案定义未来实现的契约，本文中的结构和接口名称均为拟新增名称。

1. 每次已接受的控制操作必须有记录，包括重复点击同一个操作而重置计时。
2. 实际风机运行时长由真实运行区间产生；临时暂停、持续关闭、等待时间不能计入风机运行。
3. 明细默认保留今天及前 9 个本地自然日，汇总保留今天及前 29 个本地自然日。
4. 保留天数与容量是两种约束：达到容量预算时允许提前删除最旧数据，必须报告截断范围和原因。
5. 进行中的操作和恢复信息独立保留；不能因为其开始时间超出明细窗口而丢掉当前状态。
6. 意外中断、缺少结束记录、未知时间都是合法数据状态，不得使整页解析失败。
7. 默认只记录 PIR 的 LOW→HIGH 触发，延续现有“活动次数”口径。PIR HIGH 不等于猫持续占用，连续触发的跨度也不等于真实如厕时间。
8. 本次不增加 PIR LOW 边沿明细；以后需要准确测量 HIGH 区间时，可新增记录类型并重新评估容量。
9. 明细分组由 App 完成：按固件事件顺序合并相邻感应，遇到下一项业务操作或运行事件即结束分组；不引入固定五分钟窗口。内部检查点、校时记录不构成展示分组边界。
10. 当前默认拓扑为 1 个区域、1 个 PIR、1 台风机；协议从首版具备多端点标识。首个多硬件实现的规划上限为 4 个传感器、2 台风机、2 个区域，实际数量由能力接口声明，不代表当前接线和固件已支持这些数量。

## 2. 当前实现中要一并修正的问题

- `StatisticsStore.cpp` 将事件放在固定 512 条的全量 RAM 数组中，达到上限后移动数组并淘汰旧记录；这不是芯片硬性上限。
- 事件已经使用二进制结构持久化，但每条新增或结束事件会重写整批双槽快照，历史越多，写入量越大。
- 风机事件主要由实际开关变化产生。风机已运行时重新设置临时排风，可能只重置控制计时而没有相应的新操作过程。
- 当前部分统计逻辑把“非感应记录”作为累计运行时长的条件，存在将暂停的配置时长误计为运行时间的风险。
- 日汇总与小时图的数据来源不同；小时图依赖仍保留的事件，明细被覆盖后可能与日汇总不一致。
- 操作的设定时长和实际时长混用，App 通过下一条事件推测暂停或关闭的结束边界，遇到重启和漏记时不可靠。
- BLE 固定以 18 字节分片、间隔 20 毫秒发送，即使实际 MTU 更大也未充分利用。
- 现有帧依赖换行和冗余尾片，缺少请求关联及分片序号；需要用明确协议处理重复、缺片和迟到响应。

## 3. 统一数据模型

### 3.1 标识

| 字段 | 规则 | 用途 |
|---|---|---|
| `deviceId` | 稳定的设备标识；名称变化不改变它 | 区分不同设备的缓存 |
| `dataEpoch` | 清空统计或重建格式时生成新的 128 位随机标识 | 使旧事件 ID、游标和缓存整体失效 |
| `bootId` | 每次开机生成新的 64 位随机标识 | 判断两个操作是否处在同一次开机 |
| `eventId` | 同一 dataEpoch 内单调递增的 uint32 | 排序、去重、历史分页、增量同步 |
| `operationId` | 使用操作开始记录的 eventId | 关联一次操作的开始、结束及替换 |
| `runId` | 使用一次风机归属区间开始记录的 eventId | 关联真实运行及其所属操作 |
| `sensorId` | 本设备内 uint16，1～65535，0 不表示真实传感器 | 区分传感器，与 GPIO、名称解耦 |
| `fanId` | 本设备内 uint16，1～65535，0 不表示真实风机 | 区分风机、计时、恢复与统计 |
| `zoneId` | 本设备内 uint16，1～65535，0 不表示真实区域 | 关联猫砂盆区域、传感器与风机 |
| `topologyRevision` | 拓扑配置的 uint32 递增版本 | 固定操作和查询所依据的绑定关系 |
| `groupId` | 一组已接受子操作中首个 operationId，单风机时可为 0 | 关联一次区域/批量控制，不额外复制风机操作 |

JSON 中 `dataEpoch`、`bootId` 使用十六进制字符串，避免 JavaScript 整数精度问题。eventId、operationId、runId 使用数字；eventId 不使用 0。不得在旧数据仍存在时回绕为 1；接近耗尽时拒绝继续分配，并通过受控重建开启新 dataEpoch。

sensorId、fanId、zoneId 分属各自命名空间，均可从 1 开始；缓存和引用使用 `(deviceId, endpointKind, endpointId)`，不使用名称或 GPIO 作为标识。改名、换引脚不改变 ID；删除后保留停用标记与历史名称，不把旧 ID 分配给新硬件。清空统计只改变 dataEpoch，不能顺带重编号现有端点。

### 3.2 时间

- 运行计时：使用本次开机的单调时钟，内存中按 uint64 毫秒计算，避免手机校时导致运行时长变化。
- 日历定位：UTC 秒及当时设备配置的 UTC 偏移，供按自然日查询、分桶和展示。
- 每个 bootId 保存时间锚点，锚点关联单调计时与 UTC。首次校时可以回填同次开机的未校时记录。
- 后续校时建立新的锚点；已经确认的历史定位不随新的校时重复平移。持续运行的时长仍按单调时钟计算。
- 重启前未校时且没有可信锚点的记录保留为“时间未知”，不强行放进今日或昨日。单独允许查询这些记录。
- UTC 偏移作为设备统计配置，不随每位连接者手机时区静默改变。时区变更需明确生效点；已生成历史桶不重新贴到新日期。
- 查询指定日期采用设备统计时区，App 显示该时区；普通 Unix 查询采用 `[start, end)`。

### 3.3 记录类型及含义

| 类型 | 关键内容 | 产生时机 |
|---|---|---|
| `PIR_TRIGGER` | subject 为传感器 ID，拓扑版本由所在分段记录 | LOW→HIGH |
| `OP_START` | subject 为风机 ID，operationId、groupId、模式、设定时长、延迟、来源、环境 | 控制操作被接受或自动排风过程开始 |
| `OP_END` | subject 为风机 ID，operationId、实际经过时长、结束原因、时长质量 | 正常完成、被替换、PIR 中断、明确取消 |
| `RUN_START` | subject 为风机 ID，runId、operationId、排风类型 | 风机实际开启，或开启状态下操作归属发生变化 |
| `RUN_END` | subject 为风机 ID，runId、实际运行毫秒、结束原因、时长质量 | 风机实际停止，或运行归属发生变化 |
| `AUTO_SELECTED` | subject 为风机 ID，来源、环境 | 用户主动恢复自动感应 |
| `CLOCK_ANCHOR` | UTC 秒、单调计时、UTC 偏移 | 首次或后续校时 |
| `BOOT` / `SHUTDOWN_INTENT` | 启动原因或准备重启原因 | 启动、可控重启/OTA 前 |

业务枚举由一个协议清单定义；固件和 App 分别生成或维护严格对应的常量，并通过固定样例检验。数字值发布后不得改义或复用；未知类型可保留原始数据并显示“暂不支持的事件”。本版编码分配如下：

| 枚举 | 固定编码 |
|---|---|
| 记录类型 | PIR_TRIGGER=1、OP_START=2、OP_END=3、RUN_START=4、RUN_END=5、AUTO_SELECTED=6、CLOCK_ANCHOR=7、BOOT=8、SHUTDOWN_INTENT=9 |
| 操作模式 | AUTOMATIC=1、MANUAL=2、PAUSE=3、FORCE=4、LOCKED_OFF=5 |
| 来源 | AUTOMATIC=1、BLE=2、HTTP=3、SYSTEM=4；后续来源另分配编码 |
| 环境 | PRODUCTION=1、DEV=2 |
| 结束原因 | COMPLETED=1、REPLACED=2、RESTARTED=3、PIR_INTERRUPTED=4、CANCELLED=5、REBOOT_INTERRUPTED=6、UPGRADE_RESTART=7、OWNER_CHANGED=8 |
| 时长质量 | UNKNOWN=0、EXACT=1、CONFIRMED_MINIMUM=2、INFERRED=3 |

OP_START 的 operationId、RUN_START 的 runId 均直接使用本条 eventId，不重复占用 payload；引用它们的结束记录才保存关联 ID。

模式至少覆盖：自动排风、临时排风、临时暂停、强制排风、持续关闭。来源至少覆盖：自动状态机、BLE、HTTP、系统恢复；预留联网来源编码。PRODUCTION/DEV 保存在操作中，避免两个环境的记录无法区分；默认统计全部环境，可筛选，设备诊断与页面应标明口径。

### 3.4 操作、运行与界面的一致性

1. 每台风机同一时刻最多存在一个有效控制过程；不同风机允许并行，没有排队等待的操作队列。
2. 再次点击相同限时操作：结束旧过程，原因为 `RESTARTED`；创建新过程并从新设定时长开始。
3. 点击其他操作：结束旧过程，原因为 `REPLACED`；创建新过程。
4. 风机未关闭但操作归属改变：结束旧的运行归属区间，再在同一单调时刻建立新区间，不切换继电器，不重叠计时。
5. 临时排风遇 PIR：先立即停风，再记录结束，原因为 `PIR_INTERRUPTED`。
6. 临时暂停、持续关闭没有风机运行区间。它们的实际经过时间只用于操作历史。
7. 延迟启动属于操作过程，不属于风机运行。零延迟按立即执行处理。
8. 拒绝执行的指令不产生 OP_START；记录到诊断日志，并给调用端明确错误。
9. OP_START/OP_END 在 App 可还原成一行操作历史；底层日志条数、界面分组数、操作次数分别命名，不混用。
10. UI 按相邻且同 sensorId 的 PIR 触发分组，不把不同猫砂盆的交错触发混成一段；翻页加载更多时允许首尾活动组扩大，去重仍以 eventId 为准。单传感器体验与现有规则一致。

### 3.5 端点注册表与默认配置

拓扑使用一个有版本的端点注册表，小型 A/B 配置快照可靠保存；存储格式可升级，GPIO 只能由固件的硬件适配层使用。

| 对象 | 必需字段 | 扩展字段 |
|---|---|---|
| Sensor | sensorId、type、name、enabled | driver、pinBinding、activeLevel、状态质量 |
| Fan | fanId、name、enabled、guardPolicy | driver、relayBinding、activeLevel、对应时序配置 |
| Zone | zoneId、name、enabled、sensorIds、fanIds | 显示顺序、用户备注 |

当前默认：sensorId=1 的 PIR、fanId=1 的风机、zoneId=1 的猫砂盆区域。风机 1 的输入、继电器和板载灯沿用现有接线；新增 ID 不代表自动分配空闲 GPIO。每个传感器可被多个区域引用，每个区域可引用多台风机，一台风机也可服务多个区域。

拓扑校验：ID 唯一，引用存在，无重复绑定，启用的自动风机至少有一个有效保护传感器；多个不同物理端点不能误用同一 GPIO 或驱动通道。相同物理传感器共享给两个区域应复用同一 sensorId。端口、供电、驱动电流和启动电流是否足够由硬件实施单独核对。

删除或停用仍被启用风机引用的传感器必须先提供有效替代绑定，不能把删除当作“始终无人”。改名保留历史身份；删除端点保留历史档案，至少覆盖尚存明细和汇总。

### 3.6 传感器与风机联动

对一台风机，自动保护传感器集合是“引用该风机的所有启用区域内启用传感器”的去重并集。首版 PIR 策略固定为：任一输入有活动立即停风；全部输入连续无活动达到该风机离开确认时间，才开始一轮自动排风。

| 拓扑 | 规则 |
|---|---|
| 两个区域、两个 PIR、一台共用风机 | 任一 PIR 有活动，共用风机停止；所有关联 PIR 连续无活动后排风 |
| 两个区域、两个 PIR、两台独立风机 | 各区域 PIR 只影响其关联风机；其他风机可继续运行 |
| 一个 PIR 保护多台风机 | 触发同时影响所有相关风机，各台独立结束操作并记录原因 |

自动排风、普通临时排风均服从该风机的保护集合。强制排风可限时忽略 PIR，沿用现有确认和提示，不升级为无时限。暂停、持续关闭只影响目标风机，不让另一台风机自动跟随停止。

传感器运行状态区分 HIGH、LOW、UNKNOWN、FAULT、DISABLED；有 UNKNOWN/FAULT 的保护输入时，默认阻止该风机自动/普通排风，报告受影响 sensorId。数字 PIR 无诊断线时，不能保证检测拔线或卡死，只能报告驱动实际可观察的故障。后续温湿度等传感器用独立类型和事件，不默认参与 PIR 保护；有能力的输入通过策略适配后再加入。

每台风机独立维护模式、阶段、时序、PIR 保护结果和操作/运行 ID。系统 PRODUCTION/DEV 环境仍为设备级，每台风机分别存两套时序；切换环境按现有规则结束全部活动操作、先停全部风机，再统一进入新环境，不能半台 DEV 半台正式。

### 3.7 单台、区域与批量控制契约

所有控制命令必须明确 target：`fan` + fanId、`zone` + zoneId，或 `fans` + fanIds。未指定 target 时返回错误；单风机 App 可自动填 fanId=1，协议层不把省略目标解释成全部风机。

命令包含 topologyRevision、mode、durationSeconds、delaySeconds、replace 与各目标的状态版本。区域命令在接受时把区域解析成去重后的 fanIds，整个操作使用这一份目标快照。命令响应返回 groupId、每台 fanId 的 operationId 和接受结果；群组条数不与单风机操作次数混用。

1. 批量命令先校验所有目标、PIR、时序、能力、替换条件和拓扑版本；任一不满足时整体拒绝，不先执行一半。
2. 通过后在同一控制循环派发各台子操作。这是统一接受，不承诺两只继电器在电气上绝对同时切换；接受后若发生硬件或存储故障，返回逐台状态，不声称物理原子事务，也不为回滚而重新启动已停止风机。
3. 操作替换确认返回目标列表和对应状态版本；用户确认后版本已变化则重新确认，不能覆盖另一位客户端刚发起的新操作。
4. 拓扑版本不一致返回 `TOPOLOGY_CHANGED`，App 刷新列表；不能把旧 zoneId 解释成新的风机集合后继续执行。
5. 针对一台风机的新指令只替换这台的旧操作；同 groupId 中其他风机继续。对整个组再次操作时仍显式携带新的目标列表。
6. 持续关闭、强制排风、恢复自动均服从目标范围。全设备关闭必须显式选择全部风机，确认框列出目标数量，避免无意全停。
7. commandId 标识一次用户意图；同一次请求重试不生成新 operationId。设备至少保存当前开机最近 32 个接受结果用于去重；跨重启查不到结果时返回未知，不自动重放。用户再次点击属于新的 commandId，按重置规则执行。

拓扑变更先校验容量和驱动绑定，受影响风机若有操作需确认结束、停风后才应用；注册表 A/B 提交成功后递增版本并开启新日志段，失败保持原拓扑。新启用风机进入其启动冷静期，不因新关联的 PIR 当前为 LOW 就立即排风；不受影响风机继续运行。环境切换与拓扑变更串行处理。

示例请求（字段为拟定业务契约，不代表当前接口已存在）：

```json
{
  "commandId": "c61c9328299d4fe889be126c3d99a170",
  "topologyRevision": 3,
  "target": {"kind": "zone", "id": 1},
  "mode": "manual",
  "durationSeconds": 60,
  "delaySeconds": 0,
  "replace": false
}
```

若区域 1 包含风机 1 和 2，响应明确列出两台的 operationId，并关联同一个 groupId。执行中单独暂停 fanId=1 后，fanId=2 的剩余时间不被重置。需要替换确认时，响应额外返回目标状态版本与确认 token；后续确认必须携带该 token。

现有继电器接线没有转速反馈，“确认运行”指驱动输出已经开启及其计时，不代表已测量电机机械转动或有效风量。将来增加转速/电流反馈时，用独立能力和事件记录异常，不改变现有运行字段含义。

## 4. 意外中断与时长兜底

### 4.1 时长质量

| 质量 | 含义 | 是否计入确认运行时长 |
|---|---|---|
| `EXACT` | 完整结束记录、同次开机单调计时得到 | 是 |
| `CONFIRMED_MINIMUM` | 中断前最后检查点确认的累计时长 | 已确认部分计入 |
| `INFERRED` | 有明确关联的后续替换，能用同次开机计时推算 | 单独保存、展示；默认不混入确认总量 |
| `UNKNOWN` | 没有足够可信信息 | 否，不能转为 0 |

配置时长属于计划值，不用于填充实际值。下次开机时间不能作为上次实际结束时间。来源质量由固件判定并返回，App 不自行升级为 EXACT。

完整结束缺失时，只有明确关联 operationId/runId、同 bootId 的可信替换记录，才允许推算。任意“下一条事件”不能充当结束记录；PIR 事件尤其不能用于结束暂停或持续关闭。

### 4.2 恢复检查点

默认运行或限时过程每 30 秒写入一次小型恢复检查点；可配置，但不是每秒保存全量历史。一个检查点按 fanId 保存所有活动风机的操作与运行区间 ID、已确认累计时长，另含 bootId、拓扑版本、汇总恢复位置和必要当前配置快照，不为每台风机建立相互独立、可能重复累计系统运行的恢复水位。

- 检查点使用 A/B 小文件、递增 generation、CRC 和完整长度验证；始终保留上一个有效版本。
- 运行结束优先写最终结束记录，最终记录覆盖相应检查点的推测状态。
- 重启发现前 bootId 未结束的过程：标记 `REBOOT_INTERRUPTED`，使用最后可验证检查点的确认时长；没有检查点则保留 UNKNOWN。
- 能在 OTA 前正常收尾时写 `UPGRADE_RESTART`；普通烧录、拔电或异常复位只能报告实际可观察的重启原因，不保证能识别“被烧录”。
- 不恢复旧的手动排风、暂停、强制操作或持续关闭状态；延续当前行为：启动先关闭全部风机，切到正式环境，各风机执行其冷静期，再进入自动流程。重启前持续关闭的历史过程标记为中断，不能延续计算经过停电的关闭时长。
- 检查点不是界面事件，不打断相邻感应分组。

30 秒是恢复精度目标：在存储正常且检查点成功提交时，意外断电会损失最近不足一个检查点周期的未确认运行量。若写入失败，误差可能更大，必须显示存储异常，不能宣称有固定 30 秒上界。

### 4.3 写入与恢复顺序

```text
实时状态机完成安全优先的继电器动作
→ 产生带 ID 的业务记录，进入有界队列
→ 存储模块追加记录并完成校验边界
→ 更新可持久化水位
→ 推进汇总并提交小型检查点
```

PIR 停风不得等待 SPIFFS 写入。SPIFFS 单次操作可能阻塞，不能只靠“挪到 loop 后面”保证实时性；实现时需要独立、串行的存储工作任务，避免持有控制状态机锁进行文件操作，并实测最坏停风延迟。

队列容量建议初值 64，满时不得阻塞停风、不得静默丢弃。设置记录缺口标记，优先保留操作/运行结束与恢复检查点，并在恢复可写后持久化缺口范围。接口报告已产生水位与已持久化水位；断电瞬间仍在 RAM 队列中的数据可能丢失，不能承诺零丢失。

## 5. 存储格式与分段日志

### 5.1 明确编码，避免依赖结构体填充

持久化采用小端编码，禁止直接以 `sizeof(C++ struct)` 作为跨版本协议。所有整数宽度、长度、校验范围明确。

每个分段拥有 64 字节固定头：

| 字段 | 字节数 |
|---|---:|
| magic | 4 |
| storageVersion、headerLength | 2 + 2 |
| dataEpoch | 16 |
| bootId | 8 |
| segmentId、firstEventId | 4 + 4 |
| createdUptimeSeconds | 4 |
| anchorUtcSeconds、anchorUptimeSeconds | 4 + 4 |
| utcOffsetMinutes、flags | 2 + 2 |
| topologyRevision、headerCrc32 | 4 + 4 |

单条记录采用公共头、按类型编码的 payload、CRC32：

| 字段 | 字节数 | 说明 |
|---|---:|---|
| recordLength | 2 | 包含整条记录；19～128 字节 |
| type、flags | 1 + 1 | 版本内固定含义 |
| eventId | 4 | 全局排序及同步 |
| uptimeSeconds | 4 | 同 bootId 计时定位；底层用 64 位单调时钟换算 |
| subjectKind | 1 | SYSTEM=0、SENSOR=1、FAN=2、ZONE=3 |
| subjectId | 2 | 实际 sensorId/fanId/zoneId；系统记录为 0 |
| payload | 随类型 | 例如传感器 ID、操作参数、结束原因 |
| recordCrc32 | 4 | 公共头和 payload 的完整性 |

固定公共开销为 19 字节，不强求所有记录都是 12 字节。PIR 记录通过 subject 引用传感器，不重复保存编号，无额外载荷时为 19 字节；OP_END 含 operationId、uint64 实际经过毫秒、原因及质量，约 33 字节；RUN_END 含 runId、uint64 运行毫秒、原因及质量，也约 33 字节。type 表示发生什么，subject 表示哪个端点发生，避免每新增硬件就新增一套事件类型。OP_START 的 groupId 等必要字段按类型编码，不为每条记录预留三套设备 ID。

设定时长采用 uint32 秒，实际累计采用 uint64 毫秒；不使用 uint16 秒统一保存时长，避免超过约 18 小时的持续关闭等过程溢出。秒级公共定位只用于日历映射与低精度兜底，不替代最终毫秒运行测量。

### 5.2 分段策略

- 继续使用 SPIFFS，首版不自建裸 Flash 擦写和磨损管理。
- 分段文件使用平面命名，如 `ev-000001.bin`，每段目标上限 8 KiB；跨启动会话、拓扑版本或重要时间锚点变化时提前封段。分段头的拓扑版本对应记录生成时的关系，不能用当前拓扑反向修改旧事件。
- 旧段不再整体重写；新记录只追加当前段。
- 新段提交有效段头后才使用。封段元信息可由扫描记录尾部重建，不能只依赖一个可变的尾指针。
- 启动只恢复小型索引和当前段；索引损坏时可以逐段扫描重建，扫描允许进入“统计恢复中”，控制功能继续工作。
- 尾记录长度不完整或 CRC 失败：保留前面已验证记录，停止向损坏段追加，开启新段；不跳到不可信偏移继续猜测记录边界。
- 已封段中间损坏：标记相应段不完整，通过其他完整段继续服务，接口报告缺口，不让整个统计接口崩溃。
- 不把上万条明细常驻 RAM。查询按段索引定位、流式读取，再构建有字节上限的一页响应。
- 删除整个过期段，避免不断搬移全部记录。混合了过期和有效记录的边界段允许物理多保留不足一段的数据，查询仍严格按时间过滤。
- 删除仍含必要时钟锚点或活动操作上下文的段之前，先把必要恢复信息可靠提交到小型检查点。

### 5.3 预算与保留策略

建议统计分区 512 KiB，总逻辑占用目标不超过 320 KiB，给文件系统和回收留余量。小时桶按风机、传感器保存，多端点和汇总 A/B 副本会扩大元数据，不能继续按单风机估算；采用分档预算：

| 启用配置 | 明细段 | 汇总、索引、恢复、注册表预算 | 临时空间 | 合计 |
|---|---:|---:|---:|---:|
| 1 传感器、1 风机 | 240 KiB | 64 KiB | 16 KiB | 320 KiB |
| 最多 4 传感器、2 风机 | 192 KiB | 112 KiB | 16 KiB | 320 KiB |

以上为设计预算，最终按编码后桶大小和文件副本测量。中间配置选择满足元数据大小的分档。小时/日汇总及当前操作按实际存在端点保存，不能给未安装的所有可能 ID 全量预分配。增加端点之前计算新预算；若需要提前淘汰历史，拓扑变更预览必须说明影响并确认。

单风机 240 KiB 明细预算中，平均每条 24 字节约 10,200 条，32 字节约 7,600 条，40 字节约 6,100 条；多端点 192 KiB 中分别约 8,100、6,100、4,900 条，尚需扣除段头与碎片。这些是底层记录数，一个操作可产生多条记录，多风机也增加总事件量，不能把旧版每日 436 条截图直接当作新格式日负载。新增硬件必须重新验证默认 10 天留存能力，不能宣称硬件翻倍但留存不受影响。

默认目标是支持 10 天明细；以实际运行样本测量“每日字节”和高峰记录量，验证至少 30% 容量余量。15 天配置只有通过相同验收才启用。若超过预算，先删除最旧已结束段，记录 `capacity` 截断原因；如果活动上下文自身异常占满预算，则停止记录并报告错误，不删除恢复当前状态所需的数据。

建议配置：

```text
DETAIL_RETENTION_DAYS = 10
SUMMARY_RETENTION_DAYS = 30
STORAGE_LOGICAL_TARGET_BYTES = 327680
EVENT_LOG_BUDGET_BYTES = 245760   # 1 传感器、1 风机；多端点档为 196608
SEGMENT_TARGET_BYTES = 8192
RECOVERY_CHECKPOINT_INTERVAL_MS = 30000
STORAGE_QUEUE_CAPACITY = 64
```

保留期先作为固件配置，不在本次增加普通用户页面设置。改为 15 天不能恢复已经清理的数据。系统没有可信日期时不执行基于日期的删除，只执行容量保护并保留时间未知标记。

## 6. 分区与 OTA

当前板载 Flash 为 4 MiB。拟采用以下布局，最终必须与实际构建生成的分区表一致：

| 名称 | 起始地址 | 大小 |
|---|---|---|
| nvs | 0x9000 | 0x5000 |
| otadata | 0xE000 | 0x2000 |
| app0 | 0x10000 | 0x1B0000 |
| app1 | 0x1C0000 | 0x1B0000 |
| statistics（SPIFFS） | 0x370000 | 0x80000 |
| coredump | 0x3F0000 | 0x10000 |

两个 OTA 应用槽各 1,769,472 字节，统计区 524,288 字节。以现有编译体积 1,350,203 字节估算，应用槽占用约 76.3%，剩余 419,269 字节；这是当前参考值，不是新实现编译结果。

分区表变更需要一次 USB 安装新的分区表及固件，并受控初始化新统计区。普通 app OTA 不能直接当作分区升级途径。分区改变不一定自动清空所有旧字节，本次必须明确初始化而不是假定“上传后自然清空”。随后生成新的 dataEpoch，App 清除该设备对应的旧统计缓存。旧固件和旧统计协议不提供兼容读取承诺。

## 7. 统计汇总与一致性

### 7.1 汇总保留 30 天

- 独立维护 30 天小时桶（每个端点最多 720 个普通整小时桶）与 30 天日汇总；发生时区变更时保留偏移和桶边界，不假定所有本地日期永远恰好 24 小时。
- 运行时长仅由 RUN_END 或已确认的活动检查点贡献，暂停、持续关闭及等待时间不贡献。
- PIR 触发次数只由 PIR_TRIGGER 贡献；连续感应组数属于 App 展示统计，不等同于原始触发次数。
- 自动排风次数按自动过程真正开始运行计数，手动操作次数按接受的 OP_START 计数；被拒绝的操作不计数。
- 模式归属切换时可拆分 RUN 区间，但不得把一次自动过程计成多次自动启动。
- 运行跨小时或跨日时按真实区间与桶边界的交集分摊，不能全部归到开始时刻。
- 使用毫秒累计及余数，查询时再转换为秒或分钟，避免多次短运行逐条向下取整造成累计损失。
- 未确认运行量、推算量、未知或中断次数单独统计；页面默认展示确认时长，必要时附有“不完整”说明。

端点维度规则：传感器活动按 sensorId 计数，风机运行和操作按 fanId 统计；设备原始触发总次数对事件去重，不能把被两个区域引用的一个触发算两遍。单风机操作次数按子操作数计，群组命令次数按 groupId 去重，二者分别命名。

两台风机同时运行 1 分钟：`fanRuntimeMs` 累计设备运行量为 2 分钟，`ventilatingElapsedMs` 全设备存在排风的区间并集为 1 分钟。设备级小时桶保存这两个指标；恢复检查点保存各风机状态及系统并集区间的已累计值，避免重启后重复累计交叠部分。

首版区域汇总采用“查询时固定的当前关联端点集合”：选 zoneId 时固定 topologyRevision，把对应 fanIds、sensorIds 去重后读取其历史汇总，App 标为“当前关联设备统计”。两个区域共用一台风机时，两个区域各自查看可以看到该风机运行，但全设备统计不能直接相加区域数值。历史某时刻区域归属查询只在明细与对应拓扑上下文仍保留时支持；11～30 天缺少相应维度汇总时返回 `HISTORICAL_SCOPE_UNAVAILABLE`，不能伪造历史区域归属。以后如需完整的历史区域归属汇总，再扩展桶维度和容量预算。

### 7.2 防止重复累计或漏累计

1. 日志是恢复依据；汇总保存 `appliedEventId`。
2. 活动检查点对尚未结束的 runId 保存 `creditedRuntimeMs`，只累计比已确认值增加的差量。
3. 最终 RUN_END 到达时累计“最终时长减去已确认时长”的剩余部分，不能再计整段。
4. 事件应用水位、活动区间已累计值和相关小时/日汇总在同一个小型 A/B 检查点中提交。
5. 启动从有效检查点恢复，仅重放已持久化水位之后的完整记录；缺口出现时返回不完整状态。
6. 删除明细段之前，确保该段的汇总已经提交。
7. 10 天以前的明细可以删除，11～30 天的汇总仍能独立查询；不能依赖已删除明细重算这部分图表。
8. 汇总异常时，可用尚存明细重建覆盖范围；无法重建的旧日期标记缺失，不静默清零。

当前日/小时活动运行快照可以临时加上尚未持久化的实时增量，但必须标注为 live，不提前推进持久化累计水位。

## 8. 查询、分页与同步协议 V2

### 8.1 能力协商

连接先读取 capabilities，包含：`apiVersion`、`eventSchema`、`deviceId`、`dataEpoch`、固件/最低客户端版本、明细/汇总保留天数、实际最早可用时间、已持久化 eventId、水位、分页最大条数和字节数、存储健康状态、topologyRevision、实际/最大端点数量、批量控制及传感器类型能力。通过 `GET /api/v2/topology` 获取注册表；status 返回按 fanId 的状态数组及按 sensorId 的输入数组。单风机 UI 可以简化展示，数据层仍读取数组。

不要求继续解析旧统计格式。新版 App 发现协议不支持时，只允许已声明兼容的基础控制能力，统计显示明确升级提示，不尝试把未知字段当作 0。

### 8.2 原始事件查询

拟新增版本化查询接口 `GET /api/v2/events`，BLE 与 HTTP 共用查询服务。参数：

| 参数 | 规则 |
|---|---|
| `dataEpoch` | 必须与当前数据批次一致，否则返回 `DATASET_CHANGED` |
| `start`、`end` | UTC 秒，左闭右开；日期查询由设备统计时区解析 |
| `types`、`profile` | 可选类型/环境筛选 |
| `sensorIds`、`fanIds` | 可选端点筛选；ID 按所属类型校验，未知或已删除目标返回明确状态 |
| `zoneId`、`topologyRevision` | 按固定区域绑定解析目标；不能同时提交与之冲突的显式端点过滤 |
| `direction` | `older` 或 `newer` |
| `cursor` | 包含最后扫描 ID、上界、查询摘要和 dataEpoch 的不透明游标 |
| `limit` | 默认 64，硬上限 128；仍受响应字节预算约束 |
| `snapshotUpperId` | 首次由服务确定为已持久化最高 ID，后续页固定 |

不能使用 timestamp 作为唯一游标。时间可能相同、未知或被校正，顺序由 eventId 决定。游标必须绑定全部筛选、端点范围和拓扑版本；改变类型、日期或目标后重开查询。

响应包含：原始 rows、解析字典版本、下一游标、hasMore、快照上界、有效查询范围、实际保留起点、截断/缺口/时间未知标志。若用户需要总数，可在首次查询请求 `includeTotal=1`，返回该快照范围内总数；续页不反复扫描所有段计算 total。

过滤后的游标指向最后扫描的位置，确保跳过不匹配记录后不会重复扫描或陷入空页循环。查询期间段被清理且无法继续时返回 `CURSOR_EXPIRED`，App 保留已展示内容并重新拉取当前窗口，不追加错误页。

### 8.3 紧凑表示

首版继续使用 JSON，通用响应头保留可读字段，数量大的原始记录使用固定数组：

```text
row = [eventId, utcSecondsOrNull, bootRef, uptimeSeconds, type, flags, scopeRef, payload]
scopes[scopeRef] = [subjectKind, subjectId, topologyRevision]
```

bootRef 引用当前页 boots 字典，scopeRef 引用当前页 scopes 字典，避免每条重复传 bootId、拓扑版本和长名称。名称等展示信息从注册表按端点 ID 获取，不塞进每条事件。payload 按 type 解码，未知 type 可整体跳过。原始数组在数据层立即转换为强类型模型，页面禁止直接使用 row[4] 等位置下标。记录格式、HTTP 编码和 BLE 帧版本分别管理，不能用固件版本号替代所有协议版本。

日期/类型查询仍返回完整原始记录，由 App 分组；操作恢复所需、但位于时间窗口外的开始记录通过独立 `context` 返回，不计入本页条数。跨日操作详情不能因为缺少开始上下文而算错。

### 8.4 历史和增量

- 首屏：汇总及事件页并行安排到串行 BLE 请求队列中，控制请求优先；首屏响应不能偷偷携带另一套重复事件列表。
- 加载更早：固定 snapshotUpperId，沿 older 游标继续，按 `(deviceId, dataEpoch, eventId)` 去重。
- 每分钟刷新：从已确认同步水位后读取 newer 记录；分页直到捕获该次增量上界，再推进同步水位。
- 初始时只同步了首页，不能声称已下载全部历史；记录“头部同步水位”和“历史已覆盖区间”，不要把最大 eventId 当成全部数据已完整。
- OP_END/RUN_END 作为新事件加入增量流，因此结束状态不会因为开始 ID 很旧而被漏掉。
- 实时进行中状态由 status 按 fanId 返回当前 operationId/runId、live 时长、输入保护结果和状态版本；不把每秒变化写成历史事件。
- dataEpoch 改变：清除此设备旧事件、汇总、游标和进行中投影，重新同步。
- 多手机各自有缓存和游标，读取不删除设备数据，不让第一台手机“消费掉”事件。

## 9. BLE 传输

### 9.1 MTU 与页面大小

- Android 连接后尝试协商 MTU；其他系统使用平台提供的实际结果，服务端设置值不当作协商成功。
- 首版目标 MTU 185，有效值不足时回落。单次通知总长度不得超过实际 MTU−3。
- 响应编码预算建议最大 4096 字节；默认 MTU 小包链路降低为 1536 字节，并允许更少行。
- 64/128 条只代表最多行数，先触及字节预算就结束该页。必须保证至少一条合法记录能装入预算，否则返回明确错误。
- 同一连接只发送一个正在响应的事务；历史读取不能无限占满队列，用户控制优先于尚未发送的统计页。

### 9.2 分片与完整性

建议以紧凑 JSON 为消息体，外加很小的传输头，不设计整套自定义二进制业务载荷：

```text
每个通知头：requestId:uint16 + fragmentIndex:uint16
第 0 片额外消息头：frameVersion:uint8 + flags:uint8
                    + bodyLength:uint16 + bodyCrc32:uint32
后续字节：UTF-8 JSON 消息体
```

以实际 MTU 计算除去头部后的可用载荷。接收器限制总长度和片数，按 requestId 匹配，重复片只有内容相同时才忽略；发现缺片或不一致即判定该响应失败，不把半截 JSON 交给业务解析。完成长度与 CRC 检查后再解码 UTF-8。

取消冗余尾片和固定排空等待，改用明确事务边界；连接会话变化后丢弃旧请求的迟到响应。requestId 回绕时确保没有未完成事务，且旧连接帧不进入新连接解码器。

发送端在 notify 入队失败时不推进偏移，使用有界重试和背压；notify 成功只代表本地栈接受，不代表客户端业务收到。首轮保留保守发送节奏，确认扩大分片稳定后再独立评估间隔，禁止同时修改所有速度参数后只看平均速度。

缺片可令读取事务重试一次，使用相同快照范围；重复失败显示通信异常，不能把一次统计超时直接等同物理连接必然断开。控制写入未收到响应时结果是“未知”，不能自动重发并导致重置计时；先查询当前操作与请求关联信息，再决定是否提示用户重试。

## 10. App 缓存与页面

- 使用 `(deviceId, dataEpoch)` 隔离数据。预计数千至上万条原始记录时，采用 SQLite 等行式持久化方案；不再每次刷新把所有事件重新序列化写进 SharedPreferences。
- 事件以 eventId 唯一；操作投影以 operationId 唯一；缓存同步水位与对应记录同一事务提交。
- 缓存只保留设备当前明细范围；更长归档以后另做产品能力，首版不把旧缓存当作设备仍有完整历史。
- 今日/昨日查询各自自然日，不再使用滚动 24 小时。近 3/7 天从小时或日汇总计算，不依赖全部原始事件下载完成。
- 页面先显示上次缓存，异步刷新，保持卡片高度稳定；加载更早只影响列表尾部。
- 事件显示设定时长与实际时长；正常完成时用精简文案，异常时显示原因与质量。
- 未知实际时长显示“实际时长未知”，不能显示 0 秒；检查点恢复显示“已确认至少 × 秒”；可信推算显示“约 × 秒”。
- 汇总展示确认运行时长，同时能说明存在未知/推算/中断。仅展示一位小数等格式化由 UI 负责，不截断存储精度。
- 明细被容量覆盖时展示实际可查询起点；在 11～30 天只显示汇总，明确无明细。
- 诊断页记录协商 MTU、编码字节数、分片数、事务耗时、缺片/重试、已持久化水位、剩余空间和记录缺口；避免每秒全量写日志。
- 多端点时控制页提供明确的区域/风机选择，首次只选默认风机，不默认全选；当前一台风机时隐藏选择器，保持现有操作体验。所有按钮、计时、确认框和传感器状态必须归属于当前范围。
- 选择区域时若关联两台风机状态不同，显示“部分运行/多种模式”，逐台列明状态，不用一台代表整个区域；重复操作的替换确认列出实际受影响风机。
- 统计页默认设备总览，支持 sensorId/fanId/zoneId 过滤；不同范围的缓存、请求代次和游标独立，快速切换不把旧范围响应追加到新列表。显示传感器/风机名，批量结果用 groupId 关联。
- 注册表改变时刷新选择器和能力；目标被删除则停止向其发送指令，提示重新选择，不把失效选择自动转成“全部”。

## 13. 重要取舍

- 不强制每条记录 12 字节：省空间不能牺牲操作关联、实际时长和恢复信息。
- 不先引入 Protobuf/自定义完整二进制业务协议：数字数组配合实际 MTU 已能消除大量重复文本，后续以数据证明需要时再增加编码能力。
- 不把所有历史放进 RAM，不每个事件重写历史，不在实时停风路径执行文件系统写入。
- 不承诺无条件满 10 天、任意断电零损失或精确还原断电时刻；对实际保留范围、未确认时长和记录缺口提供可查询状态。
- 清空旧数据允许去掉迁移负担，但新版仍保留格式版本、能力协商、批次和校验，为下一次扩展建立明确边界。
